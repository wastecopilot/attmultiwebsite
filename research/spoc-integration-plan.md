# Order Now ↔ SPOC automation: integration plan

This plan is based only on `research/spoc-analysis.md`. The automation is a Python module with no network
API (analysis §2), so the integration has three parts:

```
Visitor's browser ──► Next.js on Vercel (/att/order page + /att/api/order/* route handlers)
                          │  HTTPS + Bearer ATTSPOC_SERVICE_KEY (server-side env only)
                          ▼
                     order-service (Python, one long-running container next to the automation)
                          │  in-process call: process_att_order(payload)
                          ▼
                     att_order_automation.py ──► Chromium ──► SPOC partner portal
                          │
                          └─► specialist queue (handoff block with the portal link; never leaves the service)
```

The visitor never talks to the automation. The browser only ever calls our own `/att/api/order/*`. Those
server routes call `order-service` with the secret key. The portal link, the service URL, internal ids, the
`detail` text and the `handoff` block never reach the browser.

---

## 1. order-service (new, `order-service/` in this repository)

This is a thin HTTP wrapper that runs in the **same process** as the automation. It needs no extra packages
beyond the automation's own `requirements.txt`: it uses Python's standard `http.server` plus one asyncio
event-loop thread.

| Endpoint | Auth | Body | Returns |
|---|---|---|---|
| `GET /healthz` | none | – | `{"ok": true}` (no configuration details) |
| `POST /v1/quotes` | Bearer | `{request_id, service_address, products}` | `202 {job_id, state: "running"}` |
| `POST /v1/handoffs` | Bearer | `{request_id, quote_job_id, customer, customer_confirmed: true}` | `202 {job_id, state: "running"}` |
| `GET /v1/jobs/<job_id>` | Bearer | – | `{job_id, kind, state: "running"}`, or `{…, state: "done", result: to_aria(result)}` |

**How the service behaves**

- **Async jobs.** A quote takes about 45–60 s, so each POST starts a background job and returns at once. The
  website polls the job.
- **Idempotency.**
  - `request_id` is generated by the browser once per action, so a double-click or a retried request returns
    the same job.
  - The service creates the `order_ref` itself (`UW` plus 8 random characters). That value becomes the
    customer's reference number.
- **Quote → handoff reuse.**
  - The service keeps each quote's exact `service_address`, `products` and `order_ref`.
  - A handoff names only `quote_job_id` and the customer. The service rebuilds the payload with the same
    `order_ref`, address, products and options, so the automation's fingerprint matches and its stored portal
    session is resumed (analysis §2.4).
  - The browser cannot change the plan or options between quote and handoff.
- **Handoff preconditions.** The quote job must have finished with `quote_ready`. Otherwise the service
  returns `409`.
- **Security.**
  - **Auth:** `Authorization: Bearer <ATTSPOC_SERVICE_KEY>`, compared in constant time. The service refuses
    to start without a key of at least 32 characters.
  - **Request limits:** bodies are capped at 16 KB and must be JSON. Unknown top-level keys return `400`.
  - **Sensitive data:** any key matching the automation's own sensitive-key pattern (SSN, DOB, card, bank,
    PIN, password …) returns `422 {status: "sensitive_data_rejected"}`. So does any free-text value that looks
    like an SSN, a card number (Luhn check) or a date of birth. Values are never logged or echoed.
- **What leaves the service.** Only `to_aria(result)` is returned. Before returning, `result["handoff"]` is
  written to the specialist queue (below) and removed.
- **Specialist queue (O-18).**
  - **Storage:** one JSON file per handoff in `ATTSPOC_SPECIALIST_QUEUE_DIR`, written with private
    permissions.
  - **Notification:** optionally, a POST to `ATTSPOC_SPECIALIST_WEBHOOK_URL`, an internal, authenticated
    endpoint the business chooses (team chat, CRM). It carries the bearer portal link, so it must never be
    a public URL.
- **Capacity.**
  - The automation runs at most `ATTSPOC_MAX_CONCURRENCY` (3) orders at once.
  - The service also refuses new jobs with `429` once `ATTSPOC_MAX_QUEUED` jobs (12) are waiting. This
    protects the partner account from floods; the website then shows the call screen.
- **Retention.** Job results are dropped after 1 hour. Artifacts and queue files follow the README's "delete
  on a schedule" rule (O-20).
- **Logging.** Job ids, kinds, statuses and durations only. The service writes no request bodies and no
  personal data. The automation's own masked log lines are left as they are.
- **Hosting.** A Docker image based on the official Playwright Python image, **one instance**, HTTPS in
  front, at least 2 GB RAM, `ATTSPOC_URL` (the partner link) set as a secret on that host only.

## 2. Website server routes (`att-site/src/app/api/order/*`, Node runtime)

| Route | Browser sends | Server does |
|---|---|---|
| `POST /att/api/order/quote` | `{requestId, plan, options, address}` | Validates strictly (only known keys, formats, sensitive check), maps `plan` to its portal plan name, calls `POST /v1/quotes`, returns `{jobId}` |
| `GET /att/api/order/status?job=<id>` | job id | Calls `GET /v1/jobs/<id>`, returns a **customer-safe view** (below) |
| `POST /att/api/order/submit` | `{requestId, quoteJobId, customer, consent: true}` | Validates strictly, calls `POST /v1/handoffs`, returns `{jobId}` |

**Server-side environment variables** (never `NEXT_PUBLIC`; all optional, none blocks the build):

| Variable | Purpose | Default |
|---|---|---|
| `ATTSPOC_SERVICE_URL` | HTTPS base URL of order-service | unset: online ordering shows the honest "please call" message |
| `ATTSPOC_SERVICE_KEY` | Shared secret, the same value as on order-service | unset: same as above |
| `ATTSPOC_QUOTE_TIMEOUT_S` | How long the page waits for a quote | 240 |
| `ATTSPOC_HANDOFF_TIMEOUT_S` | How long the page waits for the submission (a fresh run can take as long as a quote) | 240 |

`NEXT_PUBLIC_ORDER_URL` stays as an optional override. When it is set, Order Now goes to that URL instead of
`/att/order`.

**How the routes respond**

- **Caching and indexing.** Every response carries `Cache-Control: no-store` and `X-Robots-Tag: noindex`.
- **Errors.** Error bodies are generic (`{error: "invalid_request"}` and similar). They never echo input
  values, the service URL or internal detail.
- **Logging.** The routes write no logs.

**The customer-safe view (`outcome`)**, built only from what the automation returned:

| Automation status | `outcome.screen` | Extra fields passed to the browser |
|---|---|---|
| `quote_ready` | `quote` | `total`, `lines[{item, charge}]`, `options[{choice, price}]`. **Checked first:** every cart section must be `internet`, every selected option must match the customer's own answer, and the total must be present. Otherwise it becomes `call` |
| `options_required` | `options` | `groups[{key, heading, choices[{title, price}]}]`. Never `details`, which holds agent scripts |
| `address_not_found` / `address_needs_unit` / `address_ambiguous` | `address` | `reason` |
| `plan_not_found` / `product_not_available` | `plan_unavailable` | – |
| `no_offers` | `no_service` | – |
| `unexpected_cart_items` | `call` (reason `unrequested`) | no total, ever |
| `invalid_customer_details` | `details` | `fields` (for example `["email"]`) |
| `handoff_ready` | `done` | `reference` (the `order_ref`) |
| `session_expired` / `portal_error` / `timeout` | `failed` | `retryable: true` |
| everything else, unknown statuses, service unreachable, `401`, `429`, `5xx` | `failed` | `retryable: false` |

## 3. The order page (`/att/order`)

- **Arrival.** Every Order Now button links to `/att/order?plan=<offer id>&source=<page path>`.
  AttributionKeeper keeps `gclid`, `gbraid`, `wbraid` and `utm_*` on it. The old Order Now route to
  `/check-availability?intent=order` is removed.
- **Indexing and caching.**
  - The page reads `searchParams`, so it renders dynamically and Next.js sends
    `Cache-Control: private, no-cache, no-store`.
  - It is `noindex` (metadata and an `X-Robots-Tag` header) and is not in the sitemap.

**Steps**

1. **Plan.**
   - **Content:** the selected offer from `offers.ts` with its price, conditions, fine print and "Offer details
     as of" date, plus **Change plan**.
   - **Orderable online:** the five Internet plans the automation supports (Internet 300, 500, 1000, 5000
     and Internet Air; portal names verified, analysis §2.6).
   - **Every other offer** (wireless, phone, bundles, add-ons) shows the honest "please call to complete your
     order" message with Call Now.
   - **Option questions:** asked as radio groups **with nothing preselected**: AutoPay and paperless billing
     discount (all Internet plans); Extended Wi-Fi $12/mo. (Internet Air); equipment and installation (Fiber
     300, both $0, as captured). Any other group the portal asks about comes back as `options_required` and
     is shown the same way.
2. **Address.**
   - **Fields:** street, apartment or unit (optional), city, state, ZIP.
   - **Continue** starts the quote. A calm progress screen ("usually about 45 seconds; please keep this
     page open") polls every 2.5 s. A warning appears if the visitor tries to leave while it runs.
3. **Your quote.**
   - **Content:** the real monthly total returned by the automation, with every cart line and every selected
     option itemised, and "Plus taxes and fees".
   - **Unrequested items** go to the "Please call us to complete your order" screen. No total is shown.
4. **Your details.**
   - **Fields:** first and last name, phone, email, billing language, contact preference (may we reach you by
     phone or text about installation, billing and service?), and a required consent checkbox. Nothing is
     preselected. All fields are validated.
   - **Email rejected by the automation:** the same screen shows an error on the email field.
5. **Confirm and submit.**
   - **Content:** a summary and **Submit Order Request**, which starts the handoff (a short progress state).
   - **Done:** a reference number, "A specialist will contact you to complete the credit check and
     payment", and Call Now.

**Honest failures.**

- **When:** the service is not configured, is unreachable, times out, or returns any failure status.
- **Message:** "We could not complete your request online. Please call (number) to complete your order."
- **Actions:** Call Now. **Try again** appears only when the status is retryable, at most once.
- A quote or confirmation is never shown unless the automation returned it.

**Visitor leaves mid-quote.**

- The job finishes on the service, and the stored portal session expires on its own after 20–30 minutes.
- Nothing is placed, because a quote enters no personal data.
- Personal data is kept only in React state: never in the URL, `localStorage` or analytics.

**Double clicks.**

- Buttons are disabled while a request is running.
- `requestId` makes repeated requests idempotent end to end.

## 4. Security (UI and server)

- **No sensitive fields in the UI.**
  - No field anywhere asks for SSN, date of birth, card numbers or bank details.
  - Contact fields use `autocomplete` values for name, tel, email and address only.
- **Server checks, three layers:**
  1. The website routes reject unknown keys, sensitive key names and sensitive-looking values.
  2. order-service repeats the check.
  3. The automation's own schema check runs last.
- **Personal data:** none in URLs, analytics events, logs or error messages.
- **Order page:** `noindex`, no-store, not in the sitemap. The API routes are also disallowed in `robots.txt`.
- **Customer-facing wording:**
  - formal throughout;
  - says nothing about who places the order with whom;
  - never tells customers to contact AT&T.

## 5. Tracking

The instant gtag and Consent Mode snippet is untouched.

**Events**, each with `offer_id` (the plan id) and `value` (the plan's advertised monthly price from
`offers.ts`):

- `order_click` (button);
- `begin_order` (page load);
- `order_quote_started`;
- `order_quote_shown`;
- `order_step_details`;
- `order_submit`;
- `order_failed`, with a non-personal `reason` such as `address_not_found`.

They contain no personal data. Call Now tracking is unchanged.

## 6. Testing

**Mock automation.** `att-site/tests/mocks/spoc-mock.mjs` implements the order-service API with results
shaped exactly like `OrderResult` / `to_aria`. Scenarios are chosen by keywords in the street line: every
status, slow, hanging, unreachable.

**`tests/order.spec.ts` (Playwright)**

- Clicks every Order Now button on every page at 1440 px and 390 px.
- Runs the full flow for success and every failure at both widths.
- Checks the sensitive-field rejection.
- Checks for personal-data leaks in URLs, analytics and server logs.
- Checks that no fake success appears.
- Checks the event order.
- Prints a pass/fail table.

**order-service.** Unit tests with a stubbed automation cover auth, rejection, idempotency, and keeping the
handoff block inside the service.

**Live test.** The README's documented test procedure (`sample_order.json`, Internet Air, Hicksville NY test
address) permits the quote plus handoff with the test customer. Run it once through the website against a
local order-service using the real module. The automation never clicks Continue, so no credit check runs and
no order is placed.
